# Claude Coding Rules

이 Skill의 목적은 "빨리 코드를 많이 만드는 것"이 아니라
"기존 프로젝트를 안전하게 발전시키는 것"이다.

---

# 1. 코딩 전에 반드시 읽는다

사용자가 기능을 요청해도 바로 코드를 수정하지 않는다.

먼저:

1. 프로젝트 구조 확인
2. 관련 파일 찾기
3. 관련 함수/클래스/데이터 확인
4. 기존 구현 방식 파악
5. 저장 데이터와의 관계 확인
6. 테스트 방법 확인

을 수행한다.

특히 기존 기능을 수정할 때는 해당 기능의 코드를 직접 읽고 수정한다.

코드가 보이지 않는 상태에서 구조를 추측해서 구현하지 않는다.

---

# 2. 가장 작은 변경으로 해결한다

사용자가 한 가지 기능을 요청했다면 한 가지 기능을 중심으로 수정한다.

다음 행동을 피한다.

- 필요 없는 파일 대량 수정
- 전체 시스템 리팩터링
- 변수명 전체 변경
- 폴더 구조 전체 변경
- 기존 API를 이유 없이 변경
- 사용자가 요청하지 않은 기능 추가
- "더 깔끔해 보인다"는 이유만으로 대규모 구조 변경

작은 기능은 작은 수정으로 해결한다.

---

# 3. 기존 코드 스타일을 따른다

새 코드를 작성할 때 기존 프로젝트의 방식을 우선한다.

확인할 것:

- 변수명
- 함수명
- 파일 구조
- 모듈 구조
- 상태 관리 방식
- 이벤트 처리 방식
- 데이터 정의 방식
- 에러 처리 방식
- 주석 스타일

프로젝트가 이미 특정 패턴을 사용하고 있다면 새로운 패턴을 갑자기 도입하지 않는다.

---

# 4. 기존 데이터를 먼저 확인한다

포켓몬, 조합식, 시너지, 아이템, 보스 등의 콘텐츠를 추가하기 전에
기존 데이터 파일을 확인한다.

예:

- pokemon.js
- recipes.js
- synergy.js
- boss 데이터
- round 데이터
- save 데이터

실제 프로젝트의 파일 이름이 다르면 실제 파일 구조를 기준으로 판단한다.

같은 포켓몬이나 ID가 이미 존재하는지 확인한다.

중복 ID를 만들지 않는다.

---

# 5. ID와 데이터 구조를 함부로 변경하지 않는다

다음은 기존 시스템을 깨뜨릴 수 있으므로 특별히 주의한다.

- 포켓몬 ID 변경
- 등급 ID 변경
- 조합식 ID 변경
- 시너지 ID 변경
- 저장 데이터 키 변경
- 세이브 버전 변경
- 기존 enum/상수 변경

필요하다면 migration을 추가한다.

단순히 기존 값을 삭제하고 새 값으로 바꾸지 않는다.

---

# 6. 기능 구현과 리팩터링을 분리한다

사용자가 기능 추가를 요청했다면 기능 추가를 먼저 완료한다.

동시에 대규모 리팩터링을 하지 않는다.

예를 들어:

"새로운 히든 포켓몬을 추가해줘"

라는 요청을 받았다면

나쁜 접근:

- 히든 포켓몬 추가
- 데이터 구조 전면 개편
- 렌더링 시스템 교체
- 전투 시스템 리팩터링
- 파일 구조 변경

좋은 접근:

- 현재 포켓몬 구조 확인
- 히든 포켓몬에 필요한 최소 구조 추가
- 조합식 연결
- UI 연결
- 테스트

리팩터링이 반드시 필요하다면 먼저 사용자에게 알리고 범위를 분리한다.

---

# 7. 한 번에 너무 많은 문제를 해결하지 않는다

작업 중 다른 개선점을 발견해도
현재 작업과 직접 관련이 없다면 임의로 수정하지 않는다.

예:

"보스 체력을 수정해줘"

작업 중 UI 코드가 지저분한 것을 발견해도
UI 리팩터링까지 같이 하지 않는다.

필요한 개선 사항은 작업 결과에:

"추가로 발견한 개선점"

으로 기록한다.

---

# 8. 수정 전후를 비교한다

가능하면 변경 전 상태를 기준으로 다음을 확인한다.

- 어떤 파일을 수정하는가?
- 몇 줄 정도 변경하는가?
- 기존 함수의 역할이 바뀌는가?
- 다른 코드에서 호출하고 있는가?

큰 변경이라면 수정 계획을 먼저 세운다.

---

# 9. 함수 전체를 함부로 교체하지 않는다

특정 버그를 고치기 위해 함수 전체를 새로 작성하는 것은 최후의 수단으로 한다.

먼저:

- 문제 조건 확인
- 문제가 발생하는 부분 확인
- 최소 수정

을 시도한다.

전체 교체가 필요한 경우에는 기존 함수가 담당하던 기능을 빠짐없이 확인한다.

---

# 10. 상태 관리에 특히 주의한다

웹게임에서는 다음 상태가 서로 어긋나는 문제가 자주 발생한다.

예:

게임 상태
↕
DOM
↕
저장 데이터

따라서 상태를 변경할 때:

1. 실제 게임 상태가 변경되는가?
2. 화면이 갱신되는가?
3. 저장해야 하는 값인가?
4. 새로고침 후 유지되어야 하는가?

를 확인한다.

DOM만 바꾸고 실제 게임 상태를 바꾸지 않는 구현을 피한다.

반대로 게임 상태만 바꾸고 화면을 갱신하지 않는 것도 피한다.

---

# 11. 이벤트 중복을 주의한다

이벤트 리스너를 추가할 때 기존 이벤트와 중복되지 않는지 확인한다.

특히:

- 버튼 클릭
- 라운드 시작
- 라운드 종료
- 소환
- 조합
- 모달
- 키보드 이벤트
- 타이머

에서 중복 등록을 확인한다.

버튼을 한 번 클릭했는데 두 번 실행되는 문제를 반드시 고려한다.

---

# 12. 비동기 코드를 조심한다

다음 작업에서는 실행 순서를 확인한다.

- 이미지 로딩
- 저장/불러오기
- 게임 시작
- 라운드 전환
- 타이머
- 애니메이션
- 외부 데이터 로딩

"아마 먼저 실행될 것"이라고 가정하지 않는다.

Promise/async/await/이벤트 순서를 확인한다.

---

# 13. 콘솔 오류를 무시하지 않는다

작업 후 브라우저 콘솔에 오류가 발생하면
기능이 겉보기에는 작동하더라도 완료로 판단하지 않는다.

특히:

- ReferenceError
- TypeError
- undefined
- null
- failed to load resource
- JSON parsing 오류

등을 확인한다.

---

# 14. 테스트하지 않은 것은 완료라고 말하지 않는다

아주 중요한 규칙이다.

실제로 실행하지 않았다면:

"완료했습니다."

라고 단정하지 않는다.

대신:

"코드 수정은 완료했지만 실제 브라우저 실행 테스트는 하지 못했습니다."

처럼 구분한다.

실제로 테스트했다면 어떤 테스트를 했는지 간단히 기록한다.

---

# 15. 기능 구현 후 최소 검증

새 기능마다 가능한 경우 다음을 확인한다.

### 기능 테스트

요청한 기능이 실제로 동작하는가?

### 회귀 테스트

기존 관련 기능이 깨지지 않았는가?

### 콘솔 테스트

새로운 JavaScript 오류가 발생하지 않는가?

### 저장 테스트

저장 데이터가 필요한 기능이라면 새로고침 후 정상적으로 복구되는가?

---

# 16. 숫자와 밸런스 값을 하드코딩하지 않는다

이미 프로젝트에 상수나 데이터 테이블이 존재한다면 재사용한다.

예:

나쁜 방식:

damage * 1.15

가 여러 파일에 흩어져 있음.

가능하면:

BALANCE_CONFIG.damageMultiplier

같은 기존 구조를 사용한다.

단, 실제 프로젝트가 이런 구조를 사용하지 않는다면 억지로 새 시스템을 만들지 않는다.

---

# 17. 확률 로직을 수정할 때

랜덤 시스템을 수정하면 단순히 코드가 실행되는지만 확인하지 않는다.

확률의 합이 정상인지 확인한다.

예:

T1 28%
T2 28%
T3 26%
T4 15%
T5 3%

합계가 100%인지 확인한다.

확률 보정이 있는 경우:

기본 확률
→ 보정
→ 정규화
→ 최종 선택

순서를 확인한다.

특정 등급이 의도치 않게 0%가 되거나 과도하게 높아지는 상황을 확인한다.

---

# 18. 조합식 수정 시

새 조합식을 추가할 때 반드시 확인한다.

- 재료가 실제 존재하는가?
- 재료 ID가 정확한가?
- 결과물이 실제 존재하는가?
- 동일 레시피가 중복되지 않는가?
- 역방향/순환 조합이 발생하지 않는가?
- 조합 후 결과물이 정상적으로 배치되는가?
- 조합으로 인해 슬롯 수가 잘못 계산되지 않는가?
- 조합 결과가 저장되는가?

---

# 19. UI 수정 시

UI를 수정할 때 게임 로직을 불필요하게 건드리지 않는다.

가능하면:

게임 상태
→ UI 렌더링

구조를 유지한다.

UI 텍스트 하나를 바꾸기 위해 게임 데이터 구조를 변경하지 않는다.

---

# 20. 에셋을 추가할 때

이미지 파일을 코드에서 참조하기 전에 실제 파일이 존재하는지 확인한다.

확인:

- 파일명
- 확장자
- 경로
- 대소문자
- 투명 배경 여부
- 이미지 크기
- 로딩 여부

사용자가 제공하지 않은 이미지 파일을 존재한다고 가정하지 않는다.

---

# 21. 저장 시스템 변경 시

저장 데이터에 영향을 주는 기능은 일반 기능보다 신중하게 처리한다.

새 필드 추가:

기존 세이브에 해당 필드가 없을 때 사용할 기본값을 정의한다.

필드 삭제:

기존 세이브에 해당 데이터가 남아 있어도 오류가 없는지 확인한다.

구조 변경:

migration을 고려한다.

세이브를 초기화하는 방향으로 문제를 해결하지 않는다.

---

# 22. 작업 중 막혔을 때

추측으로 계속 코드를 작성하지 않는다.

다음 중 하나를 한다.

1. 관련 파일을 더 읽는다.
2. 호출 구조를 추적한다.
3. 데이터를 확인한다.
4. 실제 오류 메시지를 확인한다.
5. 사용자에게 필요한 정보만 질문한다.

특히 "파일이 없을 것 같다", "이 함수가 있을 것이다" 등의 추측을 사실처럼 취급하지 않는다.

---

# 23. 사용자가 원하는 것과 개발자가 생각하는 것을 구분한다

사용자가:

"버튼 위치를 바꿔줘"

라고 했다면 기능을 새로 설계하지 않는다.

사용자가:

"조합식을 더 재미있게 만들어줘"

라고 했다면 기존 프로젝트의 조합 구조와 밸런스를 확인한 뒤 여러 설계안을 검토한다.

요청이 명확하면 임의로 범위를 확대하지 않는다.

---

# 24. 작업 완료 보고

작업이 끝나면 다음 형식으로 간단하게 보고한다.

## 변경 사항
- 무엇을 수정했는지

## 수정 파일
- 파일명
- 주요 변경 내용

## 테스트
- 실제 실행한 테스트
- 확인 결과

## 주의 사항
- 남아 있는 문제
- 테스트하지 못한 부분

코드를 수정하지 않았다면 수정했다고 말하지 않는다.

---

# 25. 최종 원칙

이 프로젝트에서 Claude의 역할은
"코드를 마음대로 재설계하는 개발자"가 아니라
"기존 게임을 이해하고 안전하게 발전시키는 공동 개발자"다.

따라서 항상:

읽고
→ 이해하고
→ 계획하고
→ 최소 수정하고
→ 테스트하고
→ 결과를 보고한다.

빠른 구현보다 기존 시스템의 안정성을 우선한다.
