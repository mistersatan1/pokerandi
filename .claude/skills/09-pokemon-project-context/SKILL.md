# Pokemon Random Defense - Project Context

이 Skill은 일반적인 게임 개발 지침이 아니라 이 프로젝트의 고유한 설계 맥락을 유지하기 위한 것이다.

> 수치는 세션 71(2026-10) 코드 기준으로 맞췄다. 정확한 현재값은 프로젝트 루트의 `CLAUDE.md` · `VERSION.md` 맨 위 절 · `js/data/*` 가 우선한다.

## 1. 프로젝트 정체성

이 프로젝트는 브라우저에서 실행되는 포켓몬 랜덤 디펜스/오토배틀러 계열 게임이다.

핵심 재미는 다음의 반복이다.

소환 → 배치 → 전투 → 보상 → 조합/성장 → 시너지 구성 → 다음 라운드 → 보스

플레이어는 단순히 강한 유닛 하나를 만드는 것보다,
랜덤하게 얻은 포켓몬을 조합하고 시너지와 배치를 조정하여 제한된 자원으로 70라운드(노멀 기준)를 돌파하는 경험을 한다.

기존 구현을 존중하며 새로운 시스템을 추가한다.

---

# 2. 핵심 설계 방향

## 라운드

- 모드마다 길이가 다르다: 노멀 · 챌린지 70라운드, 보스 러시 20라운드, 엔드리스(끝 없음). 정의는 `js/core/RPD.js` 의 `Modes`.
- 기존의 매 라운드 긴 PREPARE 대기 구조를 유지하지 않고 전투 흐름을 끊지 않는 방향을 우선한다.
- 10라운드 단위의 보스가 중요한 난이도 체크포인트가 된다.
- 일반 라운드와 보스 라운드의 체감 차이가 있어야 한다.

## 포켓몬 등급

현재 설계의 등급 ID는 기존 RARE 등의 이름 충돌을 피하기 위해 중립적인 T1~T5 체계를 사용한다.

- T1 = 흔함
- T2 = 안흔함
- T3 = 특별함
- T4 = 희귀함
- T5 = 전설

기본 방향:

- T1: 기본 유닛
- T2: 중간 성장
- T3: 특수 조합과 전투 역할 확대
- T4: 고유 스킬을 가진 핵심 유닛
- T5: 강력한 스킬 + 패시브를 가진 최상위 일반 등급

희귀도가 높다고 무조건 모든 상황에서 강하게 만들지 않는다.
역할, 조합, 시너지와 함께 평가한다.

---

# 3. 포켓몬 콘텐츠

현재 포켓몬은 152종(1세대 151 + 왕구리) + 초월 폼 2종이다. 등급별 수량은 `js/data/pokemon.js` 에서 센다(문서에 적어 두지 않는다 — 금방 틀려진다).
등급: T1~T5 + 불멸(T6) · 초월(T7). 소환으로 나오는 것은 특별함(T3)까지이고, 희귀함 · 전설은 조합식 · 조각 상점 · 보스 보상으로만 얻는다.

포켓몬을 추가할 때는 단순히 숫자를 늘리지 않는다.

각 포켓몬에 대해 최소한 다음을 확인한다.

1. 등급
2. 타입
3. 공격 역할
4. 타겟팅 방식
5. 스킬
6. 시너지
7. 조합식에서의 재료/결과 역할
8. 다른 포켓몬과의 중복성
9. 밸런스 영향

---

# 4. 조합식 시스템

기존의 "같은 포켓몬을 아무렇게나 합쳐 진화"하는 방식에서 벗어나
레시피 기반 조합을 핵심 성장 방식으로 사용한다.

현재: 조합식 101개(경로 103 — 근육몬 · 성원숭은 OR 조합식). 정의는 `js/data/recipes.js`, 수정법은 `docs/RECIPES_GUIDE.md`.
등급별 개수는 코드에서 센다.

각 레시피는 대체로 2~3개의 재료를 사용하고
결과물은 기본적으로 한 단계 높은 등급을 만든다.

레시피를 추가할 때는 반드시 기존 레시피와 역할이 겹치는지 확인한다.

## 조합 확률 관련 방향

기본 확률 설계:

(정의: `js/data/tiers.js` 의 `SummonTable.bands` — 소환으로는 T3 까지만 나온다)

- 1~8라운드: T1 100%
- 9~16라운드: T1 72% / T2 28%
- 17~24라운드: T1 52% / T2 34% / T3 14%
- 25~32라운드: T1 50% / T2 28% / T3 22%
- 33라운드 이후: T1 50% / T2 24% / T3 26%
- 흔함은 어느 라운드에도 50% 밑으로 내려가지 않는다(`minCommonShare`)

새로운 등급이 등장한 이후에는 해당 등급의 획득 기회가 일정 기간 증가하는 보정이 존재한다.

기본 방향:
- 새 등급 등장 후 3라운드 동안 ×1.5 보정
- 레시피 재료 하나가 부족한 경우 ×1.4 보정
- 같은 종을 이미 3개 보유한 경우 해당 종의 추가 출현 ×0.5
- 특별함(T3)이 오래 안 나오는 상황을 막는 천장(pity)이 있다: 10회 안 나오면 가중치가 늘기 시작하고(`softPityAfter`), 25회에 확정(`hardPity`)

실제 구현값이 이 문서와 다르면 코드의 현재 구현을 먼저 확인하고,
변경이 필요한 경우 사용자에게 확인한다. 이 문서를 무조건 현재 코드보다 우선하지 않는다.

# 5. 샤드/중복 보상

기존의 티어 합성 시스템은 제거됐다.

대신 중복 포켓몬을 방출하여 샤드를 얻고,
샤드를 이용해 필요한 재료를 구매할 수 있는 안전장치를 사용한다.

샤드 값(방출할 때 얻는 양) — 정의는 `js/systems/ShardManager.js` 의 `GAIN`:

- T1: 1 · T2: 2 · T3: 3 · T4: 5 · T5: 8

조각 상점 가격(그 등급 재료를 살 때) — 같은 파일의 `PRICE`:

- T1: 5 · T2: 10 · T3: 25 · T4: 245 · T5: 550

새 시스템을 추가할 때 샤드가 기존 조합식의 가치를 지나치게 무너뜨리지 않는지 확인한다.

---

# 6. 시너지

시너지는 게임 화면에서 플레이어가 즉시 확인할 수 있는 핵심 시스템이다.

기본 방향:

- PC 는 화면 오른쪽 패널에, 휴대폰은 [더보기] → 시너지 시트에 표시한다.
- TFT와 비슷하게 현재 활성화된 시너지를 한눈에 확인할 수 있어야 한다.
- 어떤 포켓몬 때문에 시너지가 활성화되었는지 이해할 수 있어야 한다.
- 시너지를 늘리기 위해 의미 없는 포켓몬을 억지로 배치하는 상황을 피한다.

시너지 효과를 추가할 때:

1. 어떤 포켓몬이 기여하는지
2. 몇 마리에서 활성화되는지
3. 활성화 보상이 무엇인지
4. 다른 시너지와 조합되는지
5. 특정 조합을 지나치게 강제하지 않는지

를 확인한다.

---

# 7. 전투 시스템

기존 전투 시스템을 존중한다.

주요 요소:

- 타겟팅
- 공격 방식
- 타입 효과
- 스킬
- 오라
- 시너지
- 보스 기믹

기존에는 다양한 타겟팅 방식과 공격 스타일, 타입 효과, 오라가 존재한다.

새 스킬을 만들 때 단순히 공격력 숫자만 크게 올리는 방식보다
전투 방식 자체를 변화시키는 효과를 우선 검토한다.

예:

- 광역 공격
- 특정 타입 대상 강화
- 보스 특화
- 적 디버프
- 아군 버프
- 체력 비례 피해
- 특정 조건에서 강화

단, 지나치게 복잡한 조건을 남발하지 않는다.

---

# 8. 보스

보스는 단순히 체력만 많은 적으로 만들지 않는다.

기본적으로:

- 보스 전용 패턴
- 페이즈 변화
- 강화/분노
- 침묵
- 충격파 등

게임 플레이에 영향을 주는 기믹을 활용한다.

새 보스는 플레이어가 기존 빌드의 약점을 발견하게 만드는 역할도 한다.

보스 난이도를 올릴 때 HP만 증가시키는 방법을 최우선으로 사용하지 않는다.

---

# 9. 도감 시스템

도감은 단순한 수집 목록이 아니라 장기적인 성장 요소다.

예시 방향:

- 도감 10종 달성 → 공격력 +1%
- 도감 20종 달성 → 공격속도 +1%

도감 보너스를 추가할 때는 장기 성장 보너스가 전투 밸런스를 지나치게 압도하지 않는지 확인한다.

도감은 여러 게임을 플레이할수록 자연스럽게 누적되는 메타 성장 시스템으로 취급한다.

---

# 10. 슬롯/경제

게임에는 소환, 업그레이드, 슬롯, 방출, 이자 등의 경제 요소가 존재한다.

슬롯 확장 관련 기존 설계:

- 슬롯 구매 증가율 약 0.04/game 수준을 고려한 설계
- 라운드 보상과의 결합 여부를 검토할 수 있다.

경제 시스템을 수정할 때는 한 요소만 보지 않는다.

반드시:

소득 → 소비 → 남는 자원 → 이자 → 소환 → 조합 → 전투력

전체 순환을 확인한다.

---

# 11. 저장 시스템

저장 데이터가 존재하므로 새 기능이 저장 구조를 변경하면 반드시 확인한다.

확인 사항:

- 기존 세이브를 읽을 수 있는가?
- 새 필드의 기본값은 무엇인가?
- 버전 마이그레이션이 필요한가?
- 삭제된 시스템의 데이터가 남아 있어도 오류가 없는가?
- 잘못된 저장 데이터가 들어왔을 때 게임이 깨지지 않는가?

기존 프로젝트에는 저장 버전과 마이그레이션 개념이 있으므로 이를 무시하고 저장 구조를 임의 변경하지 않는다.

---

# 12. 숨겨진 고급 등급

기본 T1~T5와 별개로 다음과 같은 고급 콘텐츠가 이미 구현되어 있다(히든 31 · 불멸 5 · 초월 2 — 정의는 `js/data/spells.js`).

- 히든
- 초월
- 불멸

이들은 일반적인 등급 상승과 다른 특별한 조합을 사용하는 것을 기본 방향으로 한다.

예시 아이디어:

히든 왕구리:
- 발챙이 + 슈륙챙이 + 메타몽
- 콘셉트: 개구리의 왕

히든 뮤:
- 메타몽 + 폴리곤 + 뮤츠
- 콘셉트: 모든 포켓몬의 조상

위 예시는 콘텐츠 방향을 설명하기 위한 사례다(실제 조합식은 `js/data/recipes.js` · `js/data/spells.js` 를 본다).
새로운 히든/초월/불멸을 만들 때는 조합식 자체가 발견의 재미를 제공하도록 설계한다.

# 13. UI 원칙

게임의 핵심 정보는 플레이 중 한눈에 파악할 수 있어야 한다.

중요 정보:

- 현재 라운드
- 골드
- 소환 가능 여부
- 현재 포켓몬
- 시너지
- 조합식
- 보스 상태
- 핵심 보상

조합식은 플레이 영역 주변에서 쉽게 확인할 수 있도록 한다.

불필요한 정보창을 계속 띄워 플레이 영역을 가리지 않는다.

# 14. 새로운 기능을 추가할 때의 필수 체크

사용자가 새로운 기능을 요청하면 다음 질문을 내부적으로 확인한다.

### A. 기존 시스템과 충돌하는가?
- 등급
- 조합
- 시너지
- 경제
- 저장
- 라운드
- 보스

### B. 기존 데이터 구조로 구현 가능한가?

가능하면 기존 구조를 재사용한다.

### C. 새로운 전역 상태가 필요한가?

필요한 경우에만 추가한다.

### D. UI에서 플레이어가 이해할 수 있는가?

개발자가 이해하는 것과 플레이어가 이해하는 것은 다르다.

### E. 밸런스 영향은 무엇인가?

초반/중반/후반 각각 확인한다.

### F. 저장 데이터에 영향을 주는가?

영향이 있으면 migration을 검토한다.

### G. 테스트할 수 있는가?

새 기능에 최소 하나 이상의 검증 방법을 마련한다.

---

# 15. 작업 우선순위

기능 요청을 받았을 때 다음 우선순위를 따른다.

1. 기존 기능을 깨뜨리지 않는 것
2. 사용자 요구사항 충족
3. 기존 게임 디자인과 일관성
4. 플레이어가 이해하기 쉬운 UX
5. 밸런스
6. 코드 단순성/유지보수성
7. 추가적인 확장성

사용자가 명시적으로 요구하지 않은 대규모 리팩터링은 하지 않는다.

---

# 16. 매우 중요한 규칙

이 Skill의 내용과 실제 코드가 충돌하면:

1. 현재 코드의 실제 동작을 확인한다.
2. 이 문서가 오래된 것인지 확인한다.
3. 사용자의 최신 요구사항을 확인한다.
4. 임의로 어느 쪽이 맞다고 가정하지 않는다.

즉, 이 문서는 "프로젝트 맥락"이지 "코드를 무시하고 따라야 하는 절대 규칙"이 아니다.

새 기능을 구현하기 전에 관련 파일을 먼저 읽고 실제 현재 상태를 확인한다.
